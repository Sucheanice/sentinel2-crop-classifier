## 一、为什么单卡 GPU 吃不满

因为 GPU 在这条流水线里只占一小段，而这段还是串在中间的：

```
每个窗口:
  CPU: 读窗 → 组 RGB → 算亮度 → SLIC 超像素提点    ← skimage，单线程
  GPU: set_image（图像编码器前向，batch=1，一张 1008²）   ← 就是这里
  GPU: 文本提示解码 → 可选 20 个框精修 → SLIC 点二次解码
  CPU: 掩膜取值 → resize 回整窗 → 去重 → 收实例       ← numpy/shapely，单线程
  ── 然后下一个窗口
```

三个原因叠加：

1. **严格串行，没有重叠**：代码里没有 DataLoader、没有预取、没有 CUDA stream 双缓冲。CPU 准备时 GPU 干等，GPU 前向时 CPU 干等。利用率低是必然的。
2. **batch = 1**：每个窗口单独一次 `set_image`，一张图过一遍 ViT。4090 跑 bf16 的单张 1008² 前向就几十毫秒，kernel 很短，启动/同步开销占比高，GPU 根本来不及"热"起来。512×512 级的活对 4090 属于零头。
3. **CPU 段比 GPU 段长好几倍**：实测 chunk_06 在四卡上 13:11 启动，我 13:46 停它时日志已经打到 `汇总: coarse=89550 fine=48998`——**整个 GPU 推理段只用了约 30 分钟**，而单块总时长 99 分钟，剩下 60 多分钟全是 CPU 后处理。

所以 4 卡时快的那个"4 倍"，不是把一张卡用满了，而是**4 个进程各跑各的窗口**（`spawn` 出 4 个 worker，一个绑一张卡）。换成单卡，就退化成 1 个进程串行跑完所有窗口 —— GPU 段本来就短，现在更排不上队，所以你看它只有 5%。

**用了多少（刚查的）**

| 项 | 数值 |
|---|---|
| 服务器核数 | **128 核**（Hygon C86 7390 32 核 × 4 路） |
| 整机负载 | load average **5.12** —— 基本空着 |
| 我们的推理进程 | **173% CPU ≈ 1.7 核**（占整机 1.4%） |
| 分块驱动进程 | 6.6% ≈ 0.07 核 |
| 进程内线程数 | 257 个 —— 几乎全是 torch 的线程池在那闲着 |

**为什么开不出多线程**

1. **干的活不在能并行的库上**：SLIC 是 skimage 的 Cython 单线程实现；几何运算走 GEOS，也是单线程；形态学、连通域、`_resize_mask` 同理。numpy 只有在走 BLAS 的矩阵乘才会多线程，而这里全是逐元素/几何操作。
2. **Python 层有 GIL**：窗口那个 `for` 循环、掩膜组装这些纯 Python 逻辑，多线程跑不起来。
3. **torch 的 intra-op 线程帮不上**：那 257 个线程只在 CPU tensor 运算时启用，而 CPU 段基本没碰 torch（前向都在 GPU 上）。
4. **现有的并行粒度是"进程 × 卡"**，不是线程。所以 4 卡 = 4 进程真并行；单卡 = 1 进程串行。

**真正能提速的地方（不是加线程，是改并行粒度）**

- **块级并行**：8 个块互相独立，现在却是一块一块串着跑（`run_chunks` 里的顺序 for）。单进程现在 RSS 才 7 GB，整幅 OOM 是聚合阶段的问题、不是单块的——所以完全可以把 4/5/6 这些空闲卡各挂一块，**8 块分两轮跑完，总时长直接压到 1/4**。这比"多卡摊一个块"划算得多。
- **窗口级并行**：CPU 侧用多进程池专门做 SLIC + 掩膜准备，GPU 侧单独一个进程把成批窗口凑成 batch 前向——这样 GPU 才真的能吃饱。
- **后处理阶段并行**：去重、跨尺度合并、矢量化这些也能按块拆到多进程。

一句话：现在这套是"一块一块串、一窗一窗串，CPU 单线程扛大头"，GPU 是顺手用的。要快，改并行粒度（块或窗口）比抢卡有用。

## 二、改之前必须先量（否则会改错地方）

现在有个关键未知数：一块 99 分钟（4 卡）里，GPU 段约 30 分钟，剩下 65 分钟里——

- **窗口内 CPU**：SLIC + 掩膜取值 + 窗口内质心过滤（在循环里，窗口级并行能覆盖）
- **全局后处理**：`deduplicate_instances` → `_suppress_coarse_parents` → `_cross_scale_merge` → `_remove_overlap_items` → `_regularize_items` → `_filter_dark_polygons` → [clean_and_vectorize_instances()](file:///e:/工作相关/2026年/0624%20待测试数据/成果代码/sam3_win/sam3_service/geo_infer_v10.py#L1472)（**全在窗口循环之外，窗口级并行碰不到**）

这两块各占多少，直接决定窗口级并行的天花板。建议先插桩：`t_slic / t_encode / t_decode / t_extract / t_global` 五个累加器，加环境变量开关，跑 30 个窗口就能定性。**半天成本，避免改错方向。**

## 三、方案 A：单进程内预取（改动最小）

必须做的预处理改造：把 `_prepare_tile` 拆成两半——CPU 半段产出 `{rgb, raw_lum, valid_pad, slic_pts, row, col, wh, ww}`，GPU 半段单独 `_attach_image(processor, prep)`。现在拆不开就预取不了。

```python
from queue import Queue
import threading

def _producer(wins, q, src, prep_kwargs):
    for w in wins:
        try:
            q.put((w, _prepare_tile_cpu(src, w, **prep_kwargs)))   # 纯 CPU
        except Exception:
            q.put((w, None))
    q.put(None)

q = Queue(maxsize=4)                       # 有界，防内存涨
threading.Thread(target=_producer, args=(wins, q, src, kw), daemon=True).start()

while True:
    item = q.get()
    if item is None: break
    win, prep = item
    if prep is None: continue
    ctx = _attach_image(processor, prep)          # 只做 set_image
    insts = _infer_prompt_on_tile(processor, ctx, ...)
    # ↓ 原来的质心归属过滤，照旧
```

- **收益**：把"准备"从关键路径摘走。SLIC 占窗口内准备的比重越大，收益越大——细尺度窗口（588²）窗口数多、单窗更小，相对收益比粗尺度更明显。
- **风险 / 要验的点**：**GIL**。skimage 的 SLIC 是 Cython 实现，但如果不释放 GIL，后台线程跑 SLIC 时主线程的 Python 代码照样被卡住，预取就白做了。要先测：单窗口 SLIC 耗时，同时跑一个 Python 计数循环看被拖慢多少。numpy 的大数组操作（`np.where`/`sum`）会释放 GIL，但 SLIC 本体不保证。
- **量级估计**：乐观 15~25%，别期待翻倍。

## 四、方案 B：CPU 多进程准备 + GPU 批量编码（真正的提速）

这是唯一能让两边都吃饱的形态：

```
[进程池 N=8~16]  读窗/RGB/亮度/valid/SLIC → 通过队列送 rgb(3MB/窗)
        ↓
[GPU 主进程]     攒 batch=8 → 一次编码 8 张 → 逐窗解码 → 逐窗过滤
```

**批量化可行性我查了**：[set_image_batch()](file:///e:/工作相关/2026年/0624%20待测试数据/成果代码/sam3_win/sam3/model/sam3_image_processor.py#L76-L110) 是真批编码（`torch.stack` 后一次 `forward_image`），**但解码链是单图设计**——[\_forward_grounding()](file:///e:/工作相关/2026年/0624%20待测试数据/成果代码/sam3_win/sam3/model/sam3_image_processor.py#L255-L293) 读的是 `state["original_height"]`（单值）、用的是 `self.find_stage`（`img_ids` 固定 `tensor([0])`）。

所以走法只能是**批编码 + 切 state + 逐窗解码**：

```python
def encode_batch(processor, preps):
    bstate = processor.set_image_batch([Image.fromarray(p.rgb) for p in preps])
    return [_slice_to_single(bstate, i, p.h, p.w) for i, p in enumerate(preps)]

def _slice_to_single(bstate, i, h, w):

    ...
    return {"backbone_out": sliced, "original_height": h, "original_width": w}
```

**四个坑，都要处理**：

1. **`state["masks"]` 的显存**：`_forward_grounding` 把 mask 双线性插值回整窗再二值化，是 `[n_kept, 1008, 1008]` 的 GPU bool 张量——一个窗口上百实例就是上百 MB。批量后必须逐窗解码完**立刻** `.cpu()` 并释放，否则显存飘。
2. **`src` 句柄不能跨进程**：rasterio dataset 不可 pickle，每个准备进程要自己 `rasterio.open(input_path)`。
3. **搬运成本**：走 pickle 队列传 rgb 是 3 MB/窗，建议用 `shared_memory`；千万别回传掩膜。
4. **内存线不能抬**：现在一块 chunk 的实例掩膜已经 ~100 GB（RSS 实测 100.10 GB），这是 `deduplicate_instances` 做 mask 级 mutual-best（`logical_and`）非要的中间态。窗口级并行只许在"准备"和"编码"上加并行，不能去动这块。

**收益估计**：编码器批量 2~4×、准备段 N 核并行。但**天花板被全局后处理锁死**——如果全局段占 40%，整体最多 1.6×。所以第三节的插桩是前提。

## 五、一个必须说清的边界

窗口级并行**碰不到**全局后处理（去重、跨尺度合并、规则化、矢量化）。而按之前的日志，这块很可能是大头。所以：

- 如果插桩发现全局段占 >40%，**优先做块级并行**（8 块互不依赖、现在是一块一块串着跑、内存也够），几行改动就能拿到确定收益，比窗口级并行划算得多。
- 如果全局段占比低、时间都在窗口循环里，那方案 B 值得做。

两条路是正交的，可以叠加。

## 六、建议顺序

| 步 | 内容 | 风险 | 收益 |
|---|---|---|---|
| 0 | 五段插桩，跑 30 窗口定量 | 无（只加日志） | 决定后面往哪投 |
| 1 | 拆 `_prepare_tile`（CPU/GPU 分离） | 低 | 是 2、3 的前置 |
| 2 | 方案 A 预取（顺带验 GIL） | 低 | 15~25% |
| 3 | 方案 B 多进程准备 + 批量编码 | 中 | 1.6~2.5× |
| 4 | 块级并行（正交） | 低 | 接近线性的 1/N |

我的意见：**先做第 0 步和"块级并行"，这两步便宜且收益确定；窗口级并行（B）等插桩数据出来再决定值不值得动**。要不要我先把插桩那版写出来？
