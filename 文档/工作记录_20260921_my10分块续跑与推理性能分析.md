## 二、崩溃定位与修复

### 2.1 现象

八块分块（4×2）跑到第 6 块（`chunk_05`）时中止，驱动脚本发现该块没出 shp 就退出，未进入合并：

```
[09-20 18:53:32] [6/8] 推理开始（可用内存 405 GB）
[09-20 20:33:39] [6/8] 失败，中止（见 chunk_05.log）
[09-20 20:33:39] 有块失败，未进入合并
```

`chunk_05.log` 里 GPU 推理其实**已经跑完**（粗 77965 / 细 35682 → 合并 49047 → 重叠删除 34314），倒在最后的矢量化后处理：

```
File "geo_infer_v10.py", line 885, in _suppress_coarse_parents
    if inter.area / child.area < containment: continue
ZeroDivisionError: float division by zero
```

### 2.2 根因

`_suppress_coarse_parents()`（第 3 层"粗父对象抑制"）算包含率时，**子多边形面积为 0**。这类退化几何是上一步"展开 MultiPolygon"（`is_empty` 判不出零面积的塌陷环）带进来的，而 `_suppress_coarse_parents` 的执行顺序在 `_remove_invisible`（面积 ≤ 0 过滤）**之前**，所以没被拦掉。

### 2.3 修复

改服务器上的 `/data4/sam3_project/sam3_train/Code/sam3-main/sam3_service/geo_infer_v10.py`，原文件备份为 `geo_infer_v10.py.bak_20260921`（md5 `a3712715…` → `464f0134…`，语法检查通过）：

| 行 | 函数 | 改动 |
|---|---|---|
| 882 | `_suppress_coarse_parents` | 新增 `if child.area <= 0: continue`；交集判断改成 `if inter.is_empty or inter.area <= 0: continue` |
| 929 | `_cross_scale_merge` | 新增 `if fine_poly.area <= 0 or cp.area <= 0: continue`（同类除零风险，前置拦掉） |

> 另两处按面积做除法的位置（第 800 行 `deduplicate_instances`、第 1613 行重叠删除）经核查，前面已有"交集面积 ≤ 0 就 continue"的拦截，零面积操作数到不了除法，未改动。

### 2.4 修复效果

`chunk_05` 重跑后正常出图：

```
[09-21 11:31] [6/8] 推理开始（可用内存 696 GB）
[09-21 13:10] [6/8] 完成，用时 5956 s，产出 12527 个多边形
```

### 2.5 合并阶段的第二个崩溃（09-22 修复）

八块全部跑完、进入合并阶段时立即崩，报 `AttributeError`：

```
AttributeError: 'tuple' object has no attribute 'left'
  run_chunks_my10.py:  core = box(b.left, b.bottom, b.right, b.top)
```

**根因**：本机 `rasterio.windows.bounds()` 返回的是**普通元组**而不是 namedtuple（不同 rasterio 版本的返回类型不一致），实测该版本返回 `(0.0, 10.0, 10.0, 0.0)`，没有 `.left / .bottom / .right / .top` 属性。

注意这是**合并驱动脚本 `run_chunks_my10.py` 自身的 bug**，与 `geo_infer_v10.py` 的推理无关——八块 shp 都是好的。

**修复**：按序解包，`core = box(*b)`。改后重跑，合并正常完成。

## 三、四卡改单卡

### 3.1 起因

用户问"是否跑满了 0/1/6/7 的显存、能否让出几张卡"。实查结果：**每张卡上我们的进程只占约 0.9 GB**（四卡加起来不到 4 GB），而卡 0/1/7 上还有别人的服务：

| 卡 | 占用 | 归属 |
|---|---|---|
| 0 | 12.1 GB | 别人的 vLLM Qwen3-Reranker |
| 1 | 3.0 GB | 别人的 vLLM bge-m3 |
| 2 | 4.0 GB | 同事的 SAM3_Parcel_Extractor v2.0.0 |
| 3/4/5 | ~0 | 空闲 |
| 7 | 5.2 GB | 常驻 SAM3 服务（8011 端口） |

即：不是"占卡"，是"借卡排队算"。

### 3.2 改动

`run_chunks_my10.py` 里 `GPUS = "0,1,6,7"` → `"3"`（单卡走脚本里的主进程分支，不 spawn，见 `geo_infer_v10_multigpu.py` 的 `len(gpus) == 1` 分支）。已上传服务器并重启。

**代价**：GPU 段变长约 4 倍（每块 99 分钟 → 约 3 小时），`chunk_06` 需重跑（原四卡进度作废）。

## 四、GPU / CPU 利用率实测归因

### 4.1 实测数据

| 项 | 数值 |
|---|---|
| 服务器核数 | 128 核（Hygon C86 7390 32 核 × 4 路） |
| 整机负载 | load average 5.12（基本空着） |
| 我们的推理进程 | 173% CPU ≈ 1.7 核（占整机 1.4%） |
| 分块驱动进程 | 6.6% ≈ 0.07 核 |
| 进程内线程数 | 257 个（几乎全是 torch 线程池在闲置） |
| GPU 3 利用率 | 5% |
| 单块 99 分钟构成 | **GPU 段约 30 分钟，CPU 段约 65 分钟（≈ 30:70）** |

> GPU 段 30 分钟是实测：`chunk_06` 13:11:13 启动，13:46 停它时日志已打到 `汇总: coarse=89550 fine=48998`。

### 4.2 为什么 GPU 吃不满

窗口循环（粗尺度 `_process_context_windows`、细尺度 `_process_fine_tiles`）是**严格串行**的，且 CPU/GPU 段交替、无重叠：

```
每个窗口:
  CPU  读窗 → 组 RGB → 算亮度 → valid_mask → SLIC 超像素提点（skimage 单线程）
  GPU  set_image（图像编码器前向，batch=1，一张 1008²）
  GPU  文本提示解码 →（可选）20 个框精修 → SLIC 点二次解码
  CPU  掩膜取值 → _extract_instances → 窗口内质心归属过滤 → 收实例
  ── 下一个窗口
```

三条原因：

1. **无流水线**：没有预取、没有 DataLoader、没有 CUDA stream 重叠，CPU 准备时 GPU 空转，GPU 前向时 CPU 空转；
2. **batch = 1**：每窗单独一次 `set_image`，4090 跑 bf16 单张 1008² 前向只有几十毫秒，kernel 太短，启动/同步开销占比高；
3. **CPU 段比 GPU 段长得多**：SLIC（skimage）、几何运算（GEOS）、形态学/连通域全是单线程 C 实现，numpy 只在走 BLAS 时才多线程。

> 四卡快的那"4 倍"不是把单卡吃满，而是 **spawn 出 4 个进程各跑各的窗口**（一进程绑一卡）；单卡就退化成 1 个进程串行跑完所有窗口。

### 4.3 为什么 CPU 开不出多线程

1. 活儿不在能并行的库上：SLIC 是 skimage 的 Cython 单线程实现，几何运算走单线程 GEOS；
2. Python 层的窗口 `for` 循环、掩膜组装受 GIL 限制；
3. torch 的 intra-op 线程池（257 个线程）只在 CPU tensor 运算时启用，而 CPU 段基本不碰 torch；
4. 现有并行粒度是"**进程 × 卡**"，不是线程。

## 五、窗口级并行改造方案（讨论结论）

> 完整讨论过程见 `20260921代码待改动讨论方案.md`，此处只记结论。

### 5.1 前提：先量后改

一块 99 分钟里，除 GPU 30 分钟外，剩下的 65 分钟分两块，占比未知：

- **窗口内 CPU**（SLIC、掩膜取值、窗口内质心过滤）—— 窗口级并行能覆盖；
- **全局后处理**（`deduplicate_instances` → `_suppress_coarse_parents` → `_cross_scale_merge` → `_remove_overlap_items` → `_regularize_items` → `_filter_dark_polygons` → `clean_and_vectorize_instances`）—— **在窗口循环之外，窗口级并行碰不到**。

**因此必须先插桩**（`t_slic / t_encode / t_decode / t_extract / t_global` 五个累加器，跑 30 个窗口），否则会改错方向。

### 5.2 三个方案

| 方案 | 做法 | 收益 | 风险 |
|---|---|---|---|
| A 预取 | 同进程内生产者线程做 CPU 准备（读窗/RGB/亮度/SLIC），主线程做 GPU，有界队列双缓冲 | 15~25% | SLIC 若不释放 GIL 则收益落空，需实测 |
| B 多进程准备 + 批量编码 | 进程池（8~16）做准备 → GPU 主进程 `set_image_batch` 攒 batch=8 一次编码 → 切 state 逐窗解码 | 1.6~2.5× | 改动中等，见 5.3 四个坑 |
| C 彻底重构 | worker 改成"GPU 服务 + CPU 池"，窗口结果不回传掩膜 | 最大 | 会动到全局去重的前提，暂不考虑 |

### 5.3 方案 B 的四个坑

1. **解码链是单图设计**：`set_image_batch()` 是真批编码（`torch.stack` 后一次 `forward_image`），但 `_forward_grounding()` 读的是单值 `state["original_height"]`，且用固定 `img_ids=tensor([0])` 的 `find_stage`。所以只能"批编码 → 按 dim0 切 `backbone_out`（含 `backbone_fpn` 这类 list[Tensor]）→ 逐窗解码"；
2. **显存**：`_forward_grounding` 把 mask 插值回整窗再二值化，`state["masks"]` 是 `[n_kept, 1008, 1008]` 的 GPU bool 张量，单窗上百实例就是上百 MB，逐窗解码完必须立刻 `.cpu()` 释放；
3. **`src` 句柄不能跨进程**：rasterio dataset 不可 pickle，每个准备进程要自己 `rasterio.open(input_path)`；
4. **内存线不能抬**：一块 chunk 的实例掩膜已经约 100 GB（RSS 实测 100.10 GB），这是 `deduplicate_instances` 做 mask 级 mutual-best 必需的中间态；窗口级并行只许在"准备/编码"上加并行，且搬运传 rgb（3 MB/窗），绝不回传掩膜。

### 5.4 前置改造与落地顺序

**前置改造**：把 `_prepare_tile()` 拆成 CPU 半段（产出 `rgb / raw_lum / valid_pad / slic_pts / 窗口坐标`）和 GPU 半段（单独的 `_attach_image(processor, prep)`）。现在 `set_image` 是揉在 `_prepare_tile` 里的，拆不开就预取不了。

| 步 | 内容 | 风险 | 收益 |
|---|---|---|---|
| 0 | 五段插桩，跑 30 窗口定量 | 无 | 决定后续投向 |
| 1 | 拆 `_prepare_tile`（CPU/GPU 分离） | 低 | 是 2、3 的前置 |
| 2 | 方案 A 预取（顺带验证 GIL） | 低 | 15~25% |
| 3 | 方案 B 多进程准备 + 批量编码 | 中 | 1.6~2.5× |
| 4 | **块级并行（正交）** | 低 | 接近线性的 1/N |

**结论**：优先做第 0 步与"块级并行"（八块互不依赖、现在却一块一块串着跑，内存也够，改动只有几行）；窗口级并行（B）等插桩数据出来再决定。
